## 1. Налаштування оточення та запуск проєкту

Цей проєкт містить скрипти для завантаження, трансформації та аналізу музичного датасету Spotify за допомогою MongoDB.

### Крок 1. Підготовка віртуального середовища та залежностей
Для роботи скриптів імпорту та трансформації даних використовується Python та NodeJS.

```bash
# Активація віртуального оточення Python
source venv/bin/activate

# Встановлення Python-залежностей для ETL-скрипту
pip install -r requirements.txt
```

---

### Крок 2. Конфігурація файлу `.env`

Створіть у корені проєкту файл `.env` та заповніть його вашими даними для підключення до MongoDB Atlas:

```ini
MONGO_URI=mongodb+srv://user:password@cluster.mongodb.net/

```

---

### Крок 3. Порядок запуску скриптів

Для повного відтворення аналітичної бази даних з нуля, запускайте скрипти строго у наступній послідовності:

1. **Трансформація та завантаження:**
Запустіть Python-скрипт етапу ETL, який нормалізує масиви артистів та виносить аудіо-фічі у вкладені об'єкти - у папці scripts, спочатку файл 1, потім файл 2.
2. **Виконання базових запитів:**

```

3. **Виконання складних аналітичних агрегацій:**
```bash

4. **Запуск тестів індексації та оптимізації:**
```bash

## 2. Схема даних

Після етапу трансформації дані в колекції `tracks` зберігаються в денормалізованому, оптимізованому під NoSQL-документи вигляді.

### Опис структури полів:
* `_id` — унікальний ідентифікатор документа (ObjectId), що автоматично генерується MongoDB.
* `track_name` — назва музичного треку (String).
* `popularity` — індекс популярності треку від 0 до 100 за метриками Spotify (Number).
* `explicit` — маркер наявності нецензурної лексики (Boolean: `true`/`false`).
* `duration_ms` — тривалість звукового запису в мілісекундах (Number).
* `track_genre` — основний музичний жанр, до якого віднесено цей трек (String).
* `artists` — нормалізований масив рядків, де кожен елемент є окремим ім'ям виконавця (Array of Strings). Це дозволяє коректно обліковувати колаборації.
* `audio_features` — вкладений об'єкт (Embedded Document), який ізолює в собі суто акустичні та технічні характеристики аудіохвилі:
  * `danceability` — коефіцієнт танцювальності треку від 0.0 до 1.0.
  * `energy` — рівень динамічності та енергійності звучання від 0.0 до 1.0.
  * `loudness` — загальна гучність треку в децибелах (dB).
  * `speechiness` — присутність розмовної мови у треку від 0.0 до 1.0.
  * `instrumentalness` — коефіцієнт відсутності вокалу (інструментальності) від 0.0 до 1.0.
  * `valence` — рівень позитивності/радості музичного настрою від 0.0 до 1.0.
  * `tempo` — темп музичного твору в ударах за хвилину (BPM).

### Приклад документа в JSON:
```json
{
  "_id": { "$oid": "6a09ea5eaccd7601079d60cb" },
  "track_name": "As Long as You Love Me",
  "popularity": 54,
  "explicit": false,
  "duration_ms": 245800,
  "track_genre": "acoustic",
  "artists": [
    "Erato",
    "Charlotte Almgren"
  ],
  "audio_features": {
    "danceability": 0.725,
    "energy": 0.746,
    "loudness": -6.42,
    "speechiness": 0.041,
    "instrumentalness": 0.0,
    "valence": 0.512,
    "tempo": 202.996
  }
}

```

## 3. Відповіді на теоретичні запитання

### 1. Чому аудіо-характеристики винесені в окремий об’єкт `audio_features`, а не зберігаються плоско? Коли таке вкладення вигідне, а коли створює проблеми?

* **Причина винесення:** Аудіо-характеристики (такі як `danceability`, `energy`, `tempo` тощо) є окремою логічною сутністю (доменом даних), яка описує суто акустичні властивості треку, а не його загальні метадані (назву, жанр, альбом). Винесення їх в окремий об'єкт структурує документ відповідно до принципів чистого дизайну NoSQL-схем.
* **Коли вкладення (Embedding) вигідне:**
    * **Спільний доступ (Data Co-location):** Коли додаток майже завжди запитує ці дані разом із основним документом. Наприклад, на сторінці аналітики треку в плеєрі потрібні всі 12 аудіо-фіч одночасно. MongoDB дістає весь документ за одну атомарну операцію читання з диска, уникаючи дорогих операцій `JOIN`.
    * **Обмежений розмір:** Вкладений об'єкт має чітко фіксовану кількість полів і ніколи не розростеться до ліміту MongoDB в 16 МБ на документ.
* **Коли створює проблеми:**
    * **Глибока індексація:** Якщо нам потрібно побудувати багато окремих або складених (compound) індексів на поля всередині вкладеного об'єкта, синтаксис запитів та підтримка індексів стають складнішими (`audio_features.tempo`).
    * **Сумісність із BI-системами:** Деякі класичні інструменти бізнес-аналітики (наприклад, старі версії Tableau чи SQL-орієнтовані BI-конектори) очікують виключно «пласкі» реляційні таблиці. Для них вкладені JSON-структури потребують додаткового розгортання (unwinding).

### 2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?

* **Причина збереження як масив:** У реальному світі трек може мати одного, двох або десяток виконавців (колаборації, фіти). Якщо зберігати їх рядком (наприклад, `"Gen Hoshino;Jay Chou"`), база даних сприйматиме це як один суцільний текст. Перетворення на масив `["Gen Hoshino", "Jay Chou"]` робить кожного артиста окремими атомарним елементом.
* **Які запити стають простішими:**
    * **Пошук за конкретним виконавцем:** Запит стає максимально простим та швидким: `{ artists: "Gen Hoshino" }`. MongoDB «під капотом» знає, що це масив, самостійно сканує його елементи і знаходить трек, навіть якщо артист там записаний другим чи третім.
    * **Підрахунок кількості артистів на треку:** Тепер ми можемо миттєво дізнатися, чи є трек сольним, чи це колаборація, за допомогою оператора `$size` (наприклад, перевірити, чи довжина масиву `artists` більша за 1).
    * **Використання індексів (Multikey Indexes):** Ми можемо створити індекс на масив артистів. Це дозволяє миттєво фільтрувати мільйони треків за лічені мілісекунди.

### 3. Що таке `$out` і чим він відрізняється від `$merge`? Коли використовувати кожен?

Обидва оператори є фінальними етапами в Aggregation Pipeline і служать для збереження результатів агрегації в колекцію, але мають принципово різну логіку роботи:

| Критерій порівняння | Оператор `$out` | Оператор `$merge` |
| :--- | :--- | :--- |
| **Основна поведінка** | **Повний перезапис.** Створює нову колекцію або повністю очищує (дропає) існуючу, замінюючи її вміст новими документами. | **Інкрементальне оновлення.** Інтегрує результати в існуючу колекцію, зіставляючи документи за унікальним ключем (наприклад, `_id`). |
| **Робота з наявними даними** | Старі дані в цільовій колекції повністю втрачаються. | Старі документи оновлюються (`update`), відсутні — додаються (`insert`), інші залишаються недоторканими. |
| **Гнучкість налаштування** | Не має налаштувань. Просто вказується назва колекції. | Дозволяє гнучко вказувати умови (що робити при збігу ключів, а що — при відсутності). |

* **Коли використовувати `$out`:**
    * Для регулярного перестворення аналітичних зліпків даних (Data Snapshots).
    * У задачах, де дані повністю оновлюються з нуля (як у нашому ДЗ).
* **Коли використовувати `$merge`:**
    * У системах реального часу (Real-time витрики даних).
    * Для інкрементальних ETL-процесів, коли кожну годину прилітає пачка з 100 нових треків, і нам потрібно додати лише їх, не чіпаючи і не перезаписуючи інші 113 000 документів.

### 4. Для чого використовується інструкція `$unwind`?

* **Основне призначення:** Оператор `$unwind` використовується в агрегаційних конвеєрах (Aggregation Pipeline) для «розгортання» масиву всередині документа. Якщо документ містить масив із $N$ елементів, `$unwind` створює $N$ окремих копій цього документа, де замість усього масиву в полі буде записано лише один конкретний його елемент.
* **Для чого це потрібно:** * **Поштучний аналіз та фільтрація:** Без `$unwind` неможливо виконувати складні операції групування або фільтрації над окремими елементами масиву (як у Завданні 2, коли розгортали масив `artists`, щоб проаналізувати статистику кожного виконавця окремо).

### 5. Чим `$stdDevPop` відрізняється від `$stdDevSamp`?

Обидва оператори обчислюють **стандартне відхилення** (міру того, наскільки сильно значення в датасеті розкидані навколо середнього арифметичного), але вони використовують різні математичні формули залежно від природи даних:

| Критерій | Оператор `$stdDevPop` (Population) | Оператор `$stdDevSamp` (Sample) |
| :--- | :--- | :--- |
| **Об'єкт дослідження** | **Генеральна сукупність.** Використовується, коли датасет містить абсолютно *всі* можливі дані дослідження. | **Вибірка.** Використовується, коли  датасет — це лише *частка* (зріз) даних від величезного реального світу. |
| **Математична відмінність** | Знаменник формули дорівнює $N$ (кількість елементів). | Знаменник формули дорівнює $N - 1$ (коригування Бесселя для усунення зміщення вибірки). |
| **Результат** | Дає менше значення відхилення, бо ми впевнені в усіх даних. | Дає трохи більше значення відхилення, закладаючи математичну похибку на те, що у вибірку могли не потрапити якісь крайні значення. |

* Оскільки в нашому ДЗ ми аналізуємо фіксований датасет Spotify як цілісну систему (генеральну сукупність для нашого експерименту), використання оператора **`$stdDevPop`** є абсолютно коректним.

### 6. Аналіз зміни порогів фільтрації виконавців

* **Якщо знизити поріг до 1 треку:**
    * **Як зміниться результат:** Топ-10 виконавців за середньою популярністю зазнає кардинальних змін. Туди, найімовірніше, увірвуться «виконавці-одноденки» або абсолютно невідомі артисти, які мають у базі всього один-єдиний трек, але з випадково високою популярністю (наприклад, якийсь один вірусний хіт або колаборація із суперзіркою, що отримала популярність).
    * **Пояснення:** Математично середня популярність для артиста з одним треком дорівнює популярності цього єдиного треку. Це створює серйозне статистичне викривлення, оскільки один випадковий успіх прирівнюється до стабільної популярності великих дискографій. Поріг `track_count >= 5` відсікає такий «шум» і залишає лише тих, хто має стабільний каталог.
* **Якщо підняти поріг до більш ніж 50 треків (`> 50`):**
    * **Як зміниться результат:** Наш Топ-10 повністю очиститься від сучасних поп-зірок і заповниться артистами, які працюють у жанрах із величезною кількістю релізів (наприклад, класична музика, оркестри, фонова музика або виконавці з десятилітніми кар'єрами). При цьому їхня середня популярність буде значно нижчою.
    * **Пояснення:** Що більше треків у виконавця в базі, то сильніше його середня популярність прагне до «середнього по палаті», оскільки в датасетах Spotify, окрім головних хітів, завжди присутні менш відомі треки з альбомів, аудіо-записи живих виступів (Live) або ремікси, які мають низьку популярність і тягнуть загальне середнє значення вниз.

### 7. Аналіз зміни порогів фільтрації жанрів

* **Чи зміниться результат, якщо знизити поріг до 50 треків:**
    * **Як зміниться результат:** Результат для нашого конкретного датасету **не зміниться взагалі**. Топ-5 найтанцювальніших жанрів залишиться точно таким самим (`kids`, `chicago-house`, `reggaeton`, `latino`, `reggae`) з тими самими цифрами.
    * **Пояснення:** Це пов'язано зі специфікою формування вихідного датасету Spotify. Якщо звернути увагу на  `total_tracks`, для кожного топ-жанру вивелося рівно `1000`. Оскільки реальна кількість документів у кожному жанрі (1000) значно вища і за 100, і за 50, зміна цього ліміту в меншу сторону ніяк не впливає на фільтрацію і жоден із основних жанрів просто не відсікався ні в першому, ні в другому випадку.

### 8. Що змінилося в плані виконання?

Впровадження оптимального складеного (compound) індексу за правилом **ESR (Equality, Sort, Range)** кардинально змінило стратегію виконання запиту сервером MongoDB Atlas:

* **Усунення сканування всієї колекції (COLLSCAN):** Без індексу база даних була змушена прочитати з диска кожен із `113 999` документів, щоб знайти треки жанру "pop". Після створення індексу база виконує точкове сканування індексної структури, перевіряючи лише ті документи, які точно відповідають критеріям фільтрації.
* **Усунення важкого сортування в пам'яті (InMemory Sort):** У першому варіанті головною стадією плану була `SORT`. В нашому складеному індексі поле `popularity` було прописане другим (`{ "popularity": -1 }`), дані в індексі вже зберігалися заздалегідь відсортованими. Стадія сортування повністю зникла з плану, суттєво розвантаживши процесор та RAM сервера.
* **Радикальне скорочення дискових операцій:** Кількість документів, які фізично піднімалися з диска (`docsExamined`), зменшилася з **113 999** до **354** (рівно стільки, скільки було повернуто додатку `nReturned`). Це вказує на досягнення ідеальної ефективності індексу ($1:1$).

### 9. Як зрозуміти, що індекс використовується? Наведіть значення полів із explain(), які це підтверджують

Використання індексу стовідсотково підтверджується порівнянням ключових полів з об'єкта `executionStats`, отриманого через метод `.explain()`:

| Метрика / Поле з `explain()` | Значення БЕЗ індексу | Значення З індексом | Що це підтверджує |
| :--- | :--- | :--- | :--- |
| **`executionTimeMillis`** | **120 мс** | **2 мс** | Швидкість виконання запиту зросла у **60 разів**. |
| **`totalDocsExamined`** | **113999** | **354** | База більше не сканує всю колекцію, а одразу бере з диска лише 354 цільові документи. |
| **`stage` (Переможна стадія)** | **`SORT`** | **`FETCH -> IXSCAN`** | Повна зміна логіки: замість сканування колекції та сортування в пам'яті діє **`IXSCAN`** (Index Scan — сканування індексу). |

#### Конкретні рядки виведення терміналу, які є доказом для захисту:
* **До оптимізації:** `Головна стадія (stage): SORT` та `Чи використовувалось сортування в оперативній пам'яті: ТАК`.
* **Після оптимізації:** `Нова стадія виконання (stage): FETCH -> IXSCAN` — це пряме системне свідчення того, що MongoDB знайшла потрібний індекс і скористалася ним.

## 4. Аналіз та оптимізація індексів

### Завдання 4.1. Складений індекс для точного та діапазонного пошуку з сортуванням
**Запит:** Пошук жанру `"pop"`, де `danceability >= 0.7` із сортуванням за спаданням `popularity`.

#### Ключові показники з `explain()` із термінала:
* **БЕЗ індексу:**
  * `executionTimeMillis` (Час виконання): **120 мс**

## Обґрунтування Covered Query (Покривний запит)

**Запит:** `db.tracks.find({ track_genre: "pop", popularity: { $gte: 70 } });` за умови існування індексу `{ track_genre: 1, popularity: -1, audio_features.danceability: 1 }`.

**Висновок: У наданому вигляді цей запит НЕ є покривним.**

#### Обґрунтування через поля індексу:
1. **Принцип роботи Covered Query:** Запит вважається покривним лише тоді, коли MongoDB може виконати його та повернути результат, використовуючи **виключно дані з «тіла» самого індексу**, без звернення до оригінальних документів у колекції на диску (план виконання має містити стадію `IXSCAN`, але не повинен містити стадію `FETCH`).
2. **Аналіз оригінального коду:** Хоча поля, за якими відбувається фільтрація (`track_genre` та `popularity`), повністю входять до складу нашого індексу, сам запит `.find(...)` не має обмежень на вивід. За замовчуванням MongoDB намагається повернути повний документ з усім набором полів (`track_name`, `artists`, `explicit` тощо). Оскільки цих додаткових полів в індексі немає, база даних змушена застосувати стадію **`FETCH`** та прочитати **317 документів** з диска.

#### Фактичні результати з термінала для оригінального запиту:
* `Час виконання (executionTimeMillis)`: **0 мс**
* `Стадія виконання (stage)`: **`FETCH`** (Зчитування документів з диска)
* `Перевірено документів з диска (docsExamined)`: **317**
* **Висновок:** Запит не є покривним, оскільки база даних була змушена фізично підняти з диска 317 документів для зчитування полів, яких немає в індексі.

#### Трансформація у покривний запит через проєкцію:
Щоб перетворити цей запит на покривний, необхідно додати об'єкт проєкції, який явно обмежить вивід лише тими полями, що містяться в індексі, та обов'язково відключить службове поле `_id` (яке за замовчуванням завжди тягнеться з диска):

```javascript
db.tracks.find({
  track_genre: "pop",
  popularity: { $gte: 70 }
}, {
  _id: 0,          // Обов'язково виключаємо, щоб не йти на диск
  track_genre: 1,  // Береться прямо з індексу
  popularity: 1    // Береться прямо з індексу
}).explain("executionStats");
```
#### Фактичні результати з термінала після додавання проєкції:

* `Час виконання (executionTimeMillis)`: **0 мс**
* `Нова стадія виконання (stage)`: **`PROJECTION_COVERED`**
* `Перевірено документів з диска (docsExamined)`: **0**

**Фінальний висновок:** Значення **`docsExamined: 0`** та стадія **`PROJECTION_COVERED`** є головним технічним підтвердженням покривного запиту. База даних виконала операцію фільтрації та повернула результат, працюючи виключно в оперативній пам'яті (RAM) зі структурою індексу, взагалі не торкнувшись файлів колекції на диску. Це забезпечує максимальну стабільність і швидкість при масштабуванні системи.
